SECURITY / TRANSPARENCY

Security at EXEcify.

A factual overview of how EXEcify processes uploaded projects, protects temporary build data and communicates known limitations.

Important: EXEcify is an early-stage service. These safeguards reduce certain risks but do not make untrusted source code safe or guarantee that generated executables are harmless.

Upload and build flow

  • Website delivery uses HTTPS.
  • Uploads are handled by Cloudflare Workers and temporary encrypted chunks are stored in Workers KV.
  • Builds run on temporary GitHub-hosted Windows runners using the relevant toolchains.
  • Builds have time limits and upload/archive size and path checks.

Storage and deletion

Uploaded file contents and generated output chunks are encrypted with AES-256-GCM before storage in Workers KV. Source chunks are deleted after build completion or failure; output chunks are deleted after download. A 24-hour expiry is used as a fallback for abandoned jobs. Provider-level operational records and backups may follow the providers' own retention policies.

Known limitations

Build scripts and uploaded source code are untrusted input. The current build environment is not a dedicated micro-VM per job, and outbound network access is not fully disabled because dependency installation may need it. Do not upload files containing confidential information or sensitive data. Never include passwords, API keys, private keys, personal data or confidential project files.

Generated executables are currently not digitally signed by EXEcify. Some antivirus products or Windows SmartScreen may warn about new or unsigned files. EXEcify does not bypass or disable those protections.

A preliminary AI-assisted static review of selected backend components is published on GitHub. It is not an independent audit, penetration test or certification, and it documents findings and limitations.

Report a security issue

If you believe you have found a security issue, please report it privately through the contact page. Avoid posting exploit details publicly before the issue has been reviewed.

Operational checks

The service status page runs a live check against the public Worker health endpoint. It confirms that the Worker responds and can read from its Workers KV binding. It does not test GitHub Actions dispatch, runner availability, compiler toolchains or individual language builds.

Security improvements in progress

EXEcify uses upload validation, temporary storage, encryption at rest for stored chunks, build time limits and cleanup logic. The build system still executes user-supplied project code on a general-purpose hosted Windows runner. This is a known architectural limitation, not a dedicated per-job sandbox. Do not use EXEcify for sensitive or confidential projects.

Website integrity checks run automatically through GitHub Actions when website changes are pushed or proposed. These checks validate required pages, the sitemap and homepage structured data; they are not penetration tests or build-safety tests.
