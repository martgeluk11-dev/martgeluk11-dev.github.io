TRANSPARENCY / DATA HANDLING

Privacy & security.

Your project files are processed to create a Windows build. This page explains which services handle those files, how they are protected and when temporary data is removed.

In short: uploaded file contents and generated build files are encrypted in temporary storage. Source uploads are deleted when a build finishes. Downloaded build files are deleted after the download response completes. Temporary KV data also has a 24-hour expiry as a fallback.

1. Who processes your project?

  • GitHub Pages serves the EXEcify website.
  • Cloudflare Workers receives uploads, manages build jobs and serves downloads.
  • Cloudflare Workers KV temporarily stores encrypted upload and result chunks.
  • GitHub Actions runs the build on a temporary GitHub-hosted Windows runner.

Builds use language toolchains and package managers such as pip, npm, Cargo, Go, .NET and CMake. These may download project dependencies while a build is running.

2. Storage and encryption

Uploaded file contents and generated output chunks are encrypted with AES-256-GCM before they are written to Workers KV. The encryption key is held as a Cloudflare Worker secret and is not included in the website or public source files. Transfers use HTTPS.

Job metadata needed to operate a build (such as status, file names and build settings) is stored separately and is not encrypted in the same way. Do not upload passwords, API keys, private certificates or other secrets inside a project.

3. Deletion and retention

  • Uploaded source chunks are deleted from KV when the build completes or fails.
  • Generated output chunks are deleted after the download response has completed.
  • Job metadata is kept briefly so the download/status flow can finish; after a successful download its expiry is reduced to one hour.
  • KV entries have a 24-hour expiry as a fallback for abandoned jobs or interrupted cleanup.
  • The temporary Windows runner workspace is removed by the build script, and GitHub-hosted runners are temporary.

Deletion from the active KV namespace does not mean that every infrastructure backup or provider-level record is instantly erased. Provider retention and operational records are governed by their own policies.

4. Build isolation and limitations

Each build runs in a GitHub-hosted Windows runner rather than on a permanent EXEcify server. The workflow has a 25-minute overall timeout, individual build steps have timeouts, and uploads, ZIP expansion and outputs have size limits.

EXEcify does not currently enforce a custom micro-VM per build or fully disable outbound network access. Dependency installation requires network access, so untrusted project code and build scripts may run while the runner is online. Do not upload projects you do not trust, and do not treat the service as a secure environment for confidential or highly sensitive code.

5. Logs and source code

Raw compiler stdout and stderr are not returned as build error messages. Persistent Worker invocation logs and traces are disabled. The EXEcify source code is publicly available for inspection in the backend repository and website repository.

Independent review status

We have published a preliminary, AI-assisted static code review of selected backend components. It is not an independent third-party audit, penetration test or security certification. The report lists observed controls, identified issues and unverified areas. Read the security review on GitHub.

6. Antivirus warnings and signatures

Some packaging tools can produce executables that trigger antivirus false positives. EXEcify does not currently digitally sign generated executables. A successful build is not a malware scan or a guarantee that the output is safe; review your own source code and dependencies before running or distributing the result.
