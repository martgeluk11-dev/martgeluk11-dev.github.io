TRANSPARENCY / DATA HANDLING

Privacy & security.

EXEcify sends your project to external services to build a Windows app. This page lists those services, explains what data they handle and describes when temporary files are deleted.

In short: EXEcify encrypts uploaded file contents and build output before storing them temporarily. Source uploads are deleted when a build finishes. Output files are deleted after download. A 24-hour expiry is used as a fallback.

Before uploading: keep sensitive information out

Do not upload confidential or sensitive files. This includes passwords, API keys, access tokens, private keys, certificates, personal data, customer information and files you are not allowed to share. Remove secrets before uploading. EXEcify and its service providers process the files you submit. Encryption and automatic deletion do not make confidential uploads risk-free.

1. Who processes your project?

  • GitHub Pages serves the EXEcify website.
  • Cloudflare Workers receives uploads, manages build jobs and serves downloads.
  • Cloudflare Workers KV temporarily stores encrypted upload and result chunks.
  • GitHub Actions runs the build on a temporary GitHub-hosted Windows runner.

Builds use language toolchains and package managers such as pip, npm, Cargo, Go, .NET and CMake. These may download project dependencies while a build is running.

2. Storage and encryption

EXEcify encrypts uploaded file contents and generated output chunks with AES-256-GCM before storing them in Workers KV. The encryption key is stored as a Cloudflare Worker secret, not in the website or public source code. Data transfers use HTTPS.

Some job details, such as status, file names and build settings, are stored separately and are not encrypted in the same way. Do not include passwords, API keys, certificates or other secrets in your project.

3. Deletion and retention

  • Uploaded source chunks are deleted from KV when the build completes or fails.
  • Generated output chunks are deleted after the download response has completed.
  • Job metadata is kept briefly so the download/status flow can finish; after a successful download its expiry is reduced to one hour.
  • KV entries have a 24-hour expiry as a fallback for abandoned jobs or interrupted cleanup.
  • The temporary Windows runner workspace is removed by the build script, and GitHub-hosted runners are temporary.

Removing data from the active KV namespace does not instantly remove every backup or provider record. Cloudflare and GitHub handle their own operational logs and retention under their policies.

4. Build isolation and limitations

Each build runs on a temporary GitHub-hosted Windows runner. The workflow has a 25-minute time limit, individual steps have their own limits, and uploads, extracted ZIP files and outputs are size-limited.

EXEcify does not currently run each build in its own micro-VM or block all outbound network access. Builds need network access to install dependencies, and project code or build scripts may run while the runner is online. Do not upload code you do not trust or use EXEcify for confidential projects.

5. Logs and source code

EXEcify does not show raw compiler output in build error messages. Persistent Worker invocation logs and traces are disabled. The source code is public: backend repository and website repository.

Independent review status

A preliminary static review of selected backend code is available. AI assistance was used, and the review was not an independent audit, penetration test or certification. The report lists the controls and issues found, along with areas that were not verified. Read the security review on GitHub.

6. Antivirus warnings and signatures

Some packaging tools produce files that antivirus software may flag. EXEcify does not digitally sign generated EXEs. A successful build does not scan the file or prove it is safe. Check your code and dependencies before running or sharing the result.
